# Core 파일 도우미 — 작업 지침서 (v0.2.1 · 2026-09-16 세션 7: 스텝메이드 코어파일 테스트에 대한 Ken 피드백 4건 반영 — 마스터 = 오버뷰, 케이스 쪼개기는 상세 스펙, 크기 바 설명은 폭만, 진입점은 사람 확인. 과거 이관 사례 1건 검증은 아직 → 그때 v0.3)

이 지침서는 디자이너(Ken)의 언어로 쓴다. 코드 용어 대신 디자인 용어를 쓴다.
근거 실례: 로그인/온보딩 파일럿(2026-09-02, 손으로 이관) + 소식함(프로젝트 문서 → 새 Core) + Core 파일 14개 실물 구조(§6) + **스텝메이드 시연·브랜치 실행(2026-09-10~11, `docs/demo-2026-09-10-stepmade.md`)**. Ken이 지정하는 과거 이관 사례 1건으로 §3·§4 판단 규칙을 재검증하면 v0.3.

## 0. 절대 규칙

1. **판단과 실행은 다른 단계다.** 링크를 받으면 "판별 + Δ 제안"까지만 하고 멈춘다. Figma 원본에 쓰는 것은 Ken이 제안서를 승인한 뒤, 그것도 배치(묶음) 단위로 컨펌을 받으며 한다.
2. **쓰기는 브랜치 또는 사본에서만.** 원본 파일 직접 수정 금지.
3. **보고에는 항상 node-id가 들어간 Figma 링크를 붙인다.** 형식: `https://www.figma.com/design/<파일키>/?node-id=<숫자-숫자>`
4. 제안 전에 두 가지를 스스로 검증한다: "이 규칙은 누가 언제 관리하나?" / "복사-붙여넣기 이관 방식과 충돌하나?" (둘 다 통과 못 하면 제안하지 않는다)
5. 색인에 없는 Core 파일이 있을 수 있다. 판별 결과가 "새 Core"로 나오기 전에 Ken에게 "혹시 이 영역의 Core 파일이 따로 있나요?"를 먼저 묻는다.
6. **새로 만들지 말고 복붙한다** (Ken, 2026-09-11). 마스터에 들어가는 화면은 프로젝트 문서에서 작업된 프레임을 **그대로 복사**해 우리 기준(섹션·설명 바)으로 분류만 한다. 프레임 안 구조를 도우미가 다시 짜거나 고치지 않는다. 복제 직후 **원본 대조**(`scripts/figma-write/new-core-master.md` B')를 돌려 크기·위치·글자·표시·이미지가 원본과 같은지 확인하고, 남은 차이가 0이 아니면 보고한다. 같은 파일 안 복제도 셀 폭이 바뀐 적이 있으므로 예외 없음.
7. **빠뜨리지 않는다** (Ken, 2026-09-11). 프로젝트 문서의 **모든 섹션·사이즈 클래스·페이지**를 표로 훑어, 각각이 마스터의 어디에 들어갔는지 또는 왜 안 넣었는지를 제안서 §2-4 "수록 대조표"에 한 줄씩 적는다. 표에 없는 섹션이 있으면 제안서를 내지 않는다. 문서가 커버하는 가장 큰 폭의 대표(예: 데스크톱 1440)는 반드시 들어간다. "고정"·"동일" 같은 라벨은 구간 안의 중복을 빼는 근거이지 구간을 빼는 근거가 아니다.

## 1. 입력 받기

- 프로젝트 문서 링크 (필수). 페이지·섹션 node-id가 있으면 그 범위만 본다.
- **링크를 받으면 맨 먼저 Core인지 프로젝트 문서인지 가른다**: Cover 페이지의 CoverBadge(`⚜️ Core / Final` = Core, `Working` = 프로젝트)와 페이지 이름(`🌏 마스터 파일`이 있으면 Core, `✅ Mobile / ✅ Web / 📏 운영 가이드`면 프로젝트). 세션 2에서 스텝메이드 프로젝트 문서를 Core로 잘못 색인한 실수의 방지책(2026-09-10).
- 기준 정보: 프로젝트명 · 배포(예정)일 · 담당자 (링크 카드에 쓸 것). 없으면 물어본다.
- Core 색인: `core-index/core-index.json` (읽기용 `docs/core-index.md`) — 폴더 안 Core 15개 전부 수록(2026-09-09). 색인이 오래됐으면 `scripts/figma-rest/dump-core-file.py` → `build-index-entries.py`(REST, 토큰 필요) 또는 `scripts/figma/` 스크립트(MCP `use_figma`)로 다시 읽는다.
- 같은 이름의 화면이 여러 Core에 있을 수 있다(예: 왓챠파티 플레이어 — 플레이어·왓챠파티 양쪽). 후보를 고를 때 색인 전체를 검색한다.

## 2. 프로젝트 문서 읽기 (읽기 전용)

순서: `list-pages.js` → Spec/최종 시안 페이지를 `walk-page.js`(깊이 2~3) → 큰 제목 텍스트 → 필요한 화면만 스크린샷.

읽으면서 정리할 것:
- **화면 목록**: 이름 · 크기(플랫폼: 375=APP small, 768=medium, 1024=large, 1280/1560=WEB) · 어떤 상태/케이스인지
- **케이스 축**: 문서가 무엇을 기준으로 화면을 나눴나 (로그인 여부 / 데이터 있음·없음 / 카테고리 / 입력 상태 / 뷰포트 폭 …)
- **진입 경로**: 이 화면들이 어디서 들어오나 (홈 → ?, 나의 왓챠 → ?)
- **문서 안의 "확정 필요" 표시**: 아직 확정 안 된 부분은 Δ에서 "보류"로 둔다

## 3. Core 판별

### 3-1. 후보 고르기

색인의 각 Core 파일 `domain`(다루는 영역)과 마스터 페이지의 **설명 바 제목**(대분류 → 케이스 묶음)에 프로젝트 화면 이름·진입 경로를 맞춰 본다. 판별 신호는 강한 순서대로:

1. **같은 화면 이름/역할이 이미 마스터에 있다** → 그 Core. (예: 프로젝트의 "소식함 (알림이 있을 경우)" ↔ Core 소식함 APP `3:642`)
2. **플로우 페이지의 진입 프레임 이름과 맞는다** → 그 진입 프레임이 가리키는 영역의 Core. (SVOD 플로우에 "소식함" 진입 프레임이 있어도 소식함 화면 자체의 Core는 소식함 파일이다. SVOD에는 "입구"만 있다.) 진입 섹션이 있는 Core(왓챠파티·콘상페·플레이어)는 마스터의 "○○ 진입점" 마커가 이 신호의 실물이고, 플로우 페이지의 "○○ 코어 파일 링크" 텍스트가 어느 Core로 넘어가는지를 직접 말해 준다.
3. **케이스 축이 기존 설명 바 구조와 같다** → 같은 Core 안의 같은 묶음
4. 아무 데도 맞지 않는다 → 3-3

**빈 자리표시 진입 프레임 판정법** (스텝메이드 시연 2026-09-10): 신호 2의 진입 프레임이 빈 껍데기(그리드+내비게이션 바만)이고 이름이 "리스트 상세 페이지"·"기타 상세 페이지"처럼 일반명이며 "○○ 코어 파일 링크"도 없으면 = 아직 주인 없는 화면이다. 이름으로 정체를 맞히려 하지 말고 **번호 마커를 따라간다**: 플로우의 번호 텍스트(1, 2, 3…)는 진입 프레임으로 하이퍼링크(nodeID)돼 있고, 그 번호가 놓인 y 좌표가 홈 롱 프레임의 어느 로우/셀 위인지가 진입 위치다. 그 **로우 제목 텍스트를 프로젝트 문서의 예시 이름과 대조**하면 어느 자리표시가 이 프로젝트 것인지 정해진다(예: TVOD 마커 12 → "기타 상세 페이지" ← 로우 "새로 올라온 콘텐츠" 더보기 = 스텝메이드 문서의 탭바 케이스 예시 → 기타 상세 페이지가 스텝메이드 자리). 도구: `python3 scripts/figma-rest/trace-entry-markers.py <파일키> <섹션 id> [홈 프레임 id]`. 마커가 없는 입구(로우 제목·셀 유형이 프로젝트와 맞는데 번호가 없는 로우)는 Δ에 "마커 신설" 항목으로 올린다. 이런 자리표시가 여러 Core에 있으면 유형 C 후보다.

**단, 이 추적은 "후보 찾기"까지다** (Ken 교정 2026-09-16 — 스텝메이드에서 이 방법으로 고른 진입점 3곳이 실제와 달랐다). 옛 플로우 페이지의 마커는 파일마다 기준이 제각각이고(SVOD는 로우 제목 셀 · TVOD는 더보기 버튼 · 검색은 결과 유형) 최신 홈 구성과도 어긋나 있다. 그래서:
1. 진입 후보를 **표로** 낸다 — 출발 Core · 로우/요소 이름 · 근거(마커 번호 있음 / 이름만 맞음 / 추론) · 확신도.
2. **마커 번호가 실제로 달린 입구만** 진입 섹션에 넣는다. 이름·성격만 맞아 내가 추론한 입구는 넣지 말고 표에 "확인 필요"로 둔다.
3. 진입점 확정은 **프로젝트 담당 디자이너/Ken 한 줄 확인**을 받는다. 이건 문서에 답이 없는 몇 안 되는 항목이다(프로젝트 문서·운영 가이드에 진입 경로를 적는 칸이 없음 — 2026-09-16 전수 확인, "진입"이라는 낱말이 문서 전체에 0건).

**문서에서 읽어 답하는 것들** (질문으로 넘기지 않는다): 빈 상태 — 프로젝트 문서에 없으면 만들어 넣지 않는다(미수록, 기준 문서 책임) / 배포일·담당자 — 프로젝트 커버 프레임의 상태 배지(Working→Final)와 담당 텍스트에서 읽는다 / 새 Core 이름 — 프로젝트 커버의 Page Name을 그대로 쓴다(왓챠파티·소식함 선례).

### 3-2. 판별 유형

| 유형 | 조건 | 결과 |
|---|---|---|
| **A. 기존 Core 갱신** | 화면·케이스 축이 한 Core 안에 들어감 | 그 Core의 마스터 페이지에 Δ |
| **B. 여러 Core에 걸침** | 본체는 한 Core, 다른 Core에는 "입구"만 바뀜 | 본체 Core에 Δ + 다른 Core는 진입 프레임 교체 항목만 |
| **C. 새 Core** | 기존 Core의 영역 어디에도 속하지 않거나, 경계를 **가로지르는** 기능(왓챠파티·결제/구독처럼) | 새 Core 파일 제안 (규격은 §6). Ken이 파일 생성, 도우미가 내용 채움 |

경계에 걸치거나 가로지르면 "가장 가까운 Core에 끼워 넣기"보다 **새 Core**가 원칙이다 (2026-09-02 결정). 단 §0-5의 질문을 먼저 한다.

### 3-3. 확신도

- 높음: 신호 1 또는 2가 맞음
- 보통: 신호 3만 맞음 → 제안서에 근거를 쓰고 Ken 확인
- 낮음: 신호 없음 → 새 Core 후보로 두되 §0-5 질문부터

## 4. Δ 작성 — 마스터에 "무엇을 몇 장" 넣을지

### 4-1. 수록 기준 (운영안)

- **마스터는 오버뷰다** (Ken 피드백 2026-09-16, 스텝메이드 테스트). 마스터를 열었을 때 보이는 것은 **"이 기능의 화면이 크기마다 이렇게 생겼다"** 한 겹이다. 부품을 뜯어 늘어놓은 것은 **상세 스펙(기준 문서)** 몫이다. 갈리면 아래 질문으로 가른다.

| 질문 | 예 → 마스터 | 아니오 → 상세 스펙 |
|---|---|---|
| 이 케이스가 없으면 **다른 화면**을 그리게 되나? | 리스트 있을 때/없을 때, 로그인/비로그인 | 헤더 이미지 비율·그라데이션·safe area, 콘텐츠 정렬, placeholder 배치 |
| 그게 **한 부품을 어떻게 만드느냐**의 규칙인가? | — | 타이틀 로고/텍스트·줄 수, 더보기 버튼 노출 조건 |
| **모든 크기에 나란히** 붙나? | 크기마다 있는 것 | **한 크기(small)에만 붙는 케이스** = 오버뷰가 아니라는 신호 |

- **"디자인 결정이 갈리는 지점마다 한 장."** 전수가 아니라 대표. 단 위 표를 먼저 통과한 것만.
- 디폴트 2장: **기본형 + 빈 상태**. 승격 조건 3개 중 하나면 추가: ① 반쪽 분기(한 화면 안에서 케이스에 따라 절반 이상이 달라짐) ② 전파 규칙(이 결정이 다른 화면에도 적용됨) ③ 반복 질문 2회.
- **크기(뷰포트)는 대표 크기에서 케이스 전수, 재배치가 일어나는 화면만 크기별.** (기존 SVOD의 small/medium/large × 케이스 전수 나열은 구방식 — 새 이관 때 축소 후보)
- 전수는 기준 문서(플로우 페이지/프로젝트 문서)의 책임. 마스터에서 뺀 것은 §3 "넣지 않기로 한 것"에 적는다.

### 4-2. 실례에서 뽑은 판단 규칙 (로그인/온보딩 파일럿, 소식함)

| 상황 | 판단 | 실례 |
|---|---|---|
| 같은 화면이 갈래(이메일/간편/애플)마다 반복 | **1장**. 갈래 특유 화면이 없으면 그 갈래는 미수록 | 애플 갈래 미수록 |
| 입력 상태 focus / active / filled | **대표 1장** (filled) | 이름·비밀번호 입력 |
| 인증·대기 화면의 하위 상태 | 기본 + **실패/초과 1장** | 이메일 인증: 기본 + 시간 초과 |
| 바텀시트가 3개인데 내용이 같음 | 1장 | 갈래 시작 바텀시트 |
| 리스트 화면 | **있을 때 + 없을 때**(빈 상태) 각 1장. 로그인 여부가 화면을 바꾸면 비로그인 1장 추가 | 소식함 APP |
| 셀/항목 유형이 여럿 (카테고리·상태) | 화면을 늘리지 말고 **케이스 표 1장**. 단 그 유형이 **그 화면의 존재 이유**일 때만(소식 유형이 곧 소식함이다). 부품 제작 규칙이면 상세 스펙 | 소식함 "소식 유형 케이스" `9:22413` |
| 같은 화면 · 데이터만 다른 더미 | 1장 | SVOD 이미지 컨텐츠_small ×2 → 1장 |

### 4-3. Δ 구분

- **교체**: 마스터에 같은 자리가 있고 시안이 바뀜. 프레임 껍데기(이름·위치·ID)는 유지하고 내용만 바꾼다 → 기존 링크가 살아남는다.
- **추가**: 새 결정 지점. 설명 바(스크린 설명 컴포넌트)도 함께 추가. 색: 대분류 ⚫️ / 케이스 묶음 ⚪️ / 크기·단계 🔵.
- **유지**: 변화 없음 (명시해 두면 검토가 빨라진다)
- **삭제**: 마스터에서 내림. 플로우 페이지/기준 문서에는 남긴다.
- **마커 신설**: 다른 Core 플로우에 입구는 있는데 번호 마커가 없는 로우(§3-1 추적법으로 드러남). 번호 + "○○ 코어 파일 링크" 텍스트를 추가하는 항목. (v0.2, 스텝메이드 "왓챠 팀 큐레이션")
- 각 항목에 **출처 링크**(프로젝트 문서의 node-id)와 **수록 근거**(어느 결정이 갈리는지)를 적는다.

### 4-4. 링크 카드

- 카드는 **항상 1개**, 링크도 1개(기준 문서). 기준 정보 = 프로젝트명 · 배포일 · 담당자.
- 플로우가 바뀐 프로젝트면 **배턴터치**: 새 기준 문서로 링크 교체, 이전 기준 문서는 아카이브.
- 카드가 없는 Core(SVOD)는 Δ에 "링크 카드 추가"를 넣는다.

### 4-5. 제안서 형식

`templates/delta-proposal.md`를 채운다. **§2-4 수록 대조표**(§0-7)가 반드시 있어야 한다: 행 = 프로젝트 문서의 섹션/사이즈 클래스/페이지 전부, 열 = 마스터 위치(섹션 > 묶음 > 🔵) 또는 "미수록 — 이유". 도우미는 이 표의 행 수가 문서의 섹션 수와 같은지 스스로 센다. 보고 메시지에는 판별 결과 · Δ 표 · 묻는 것 · 모든 링크(node-id 포함)를 넣는다.

같은 화면이 두 Core에 사는 경우가 이미 있다: **왓챠파티 플레이어**는 [Core] 플레이어(`5:23889` 묶음)와 [Core] 왓챠파티(`7:37843` 묶음) 양쪽에 있음. 운영안 §5 "승격 후속 규칙"(다른 Core에는 진입점 화면 + 링크 카드만)대로면 플레이어 쪽은 입구만 남겨야 한다. 왓챠파티 플레이어 Δ가 생기면 **양쪽 갱신 대신 한쪽 정리**를 먼저 제안한다.
