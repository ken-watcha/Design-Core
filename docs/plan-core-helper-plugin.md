# Core 도우미 — 팀 전체가 쓰는 프로그램 설계안 (v1, 2026-09-10)

> 목적: 프로덕트 디자이너 누구나 프로젝트를 끝내고 Core 파일에 반영할 때, **같은 규격으로 · 덜 어렵게 · 덜 귀찮게** 하도록 돕는 프로그램을 만든다. 운영안(노션 "디자인 코어 파일")이 규칙이고, 이 프로그램은 그 규칙을 손 대신 실행해 주는 도구다.
> 지금까지 만든 것(색인·지침서·REST 스크립트·시연)은 이 프로그램의 **판단 규칙을 검증한 재료**이고, 프로그램 자체는 아직 없다.

## 1. 누가, 언제, 무엇이 귀찮은가

대상: 왓챠 프로덕트 디자이너 전원 (지금 Core 14개를 여러 명이 나눠 다룸).

| 시점 | 지금 손으로 하는 일 | 어려움 · 귀찮음 |
|---|---|---|
| **디자인 확정** | Δ(어디를 → 무엇으로) 메모를 적어 둔다 (권장) | 어느 Core의 어느 자리인지 찾아야 함. 마스터에 뭘 몇 장 넣을지 기준을 매번 떠올려야 함. 그래서 잘 안 적음 |
| **배포 후 이관** | ① 버전 저장 ② 화면 교체/추가(껍데기 유지) ③ 링크 카드 갱신 ④ 커버 로그 ⑤ 아카이브 | 설명 바 3단(⚫⚪🔵)을 손으로 배치, 32px 그리드 정렬, 프레임 이름 규칙, 링크 카드 형태가 파일마다 제각각(6개만 있고 기준 정보는 어디에도 없음), 커버 로그는 아무도 안 씀 |
| **새 Core 필요** | 왓챠파티처럼 파일을 새로 만들고 규격을 흉내 냄 | 규격이 머릿속에만 있음 → 웹툰은 루트 섹션 없음, TV는 구형식, 크기 접미사 파일마다 다름 |
| **다른 Core 입구** | 플로우 페이지에 진입 프레임·번호 마커·"○○ 코어 파일 링크" | 자주 빠짐 (예: 왓챠 팀 큐레이션 로우엔 마커 없음). 이름이 "기타 상세 페이지"라 나중에 아무도 모름 |

통일성이 깨지는 지점 = 위 표의 오른쪽 전부. **사람에게 규칙을 외우게 하는 대신, 프로그램이 규격대로 만들어 주면 통일성은 저절로 생긴다.**

## 2. 프로그램의 형태 — Figma 플러그인 + 규칙 엔진 + (필요할 때만) AI

```
디자이너 ── Figma 플러그인 "Core 도우미" ──┬── 규칙 엔진 (Core 색인 + 수록 기준 + 파일 규격)  ← 대부분의 일
                                          └── AI 판단 (Claude)                            ← "어느 Core인가"가 애매할 때만
```

- **왜 플러그인인가**: 디자이너는 Figma 안에서 일한다. 파일을 열고 플러그인 창에서 버튼 몇 개 누르는 것이 통일성을 만드는 가장 짧은 길이다. 플러그인은 열린 파일에 **쓸 수 있다** (섹션·설명 바·링크 카드·커버 로그 생성, 프레임 정렬, 버전 저장). 채팅형 도우미(Claude)는 판단엔 강하지만 "다른 디자이너도 매번 쓴다"엔 맞지 않다.
- **왜 규칙 엔진인가**: 파일 규격(지침서 §6)과 수록 기준(§4)은 이미 글로 정리돼 있고 대부분 조건문으로 옮길 수 있다. 규칙이 코드가 되면 사람마다 다르게 해석할 여지가 없다.
- **AI는 어디에 남나**: "이 프로젝트가 어느 Core의 어느 묶음에 들어가나"의 마지막 판단, 그리고 자리표시 프레임처럼 이름만으로 모르는 것을 근거를 대며 추론하는 일. 규칙으로 후보를 좁힌 뒤 AI가 고르고, **최종 확정은 항상 디자이너**.
- 플러그인이 다른 파일을 읽어야 할 때(색인 갱신, 프로젝트 문서의 Δ 읽기)는 Figma REST를 쓴다. 디자이너가 자기 토큰을 한 번 등록하면 플러그인이 저장해 둔다. 쓰기는 **지금 열려 있는 파일에만** — 운영안의 "원본은 담당 디자이너가 직접" 원칙과 맞는다.

## 3. 플러그인이 하는 일 4가지 (화면 흐름)

### A. 새 Core 만들기 — "빈 파일 → 규격 완성" (완전 자동)

디자이너가 빈 파일을 만들고 플러그인에서 이름만 입력하면:
1. 페이지 4개 생성: `Cover` / `---` / `🌏 마스터 파일` / `🌊 플로우_YY.MM 기준`
2. Cover 프레임 800×500: Page Name(EN/KR), CoverBadge(⚜️ Core / Final), **업데이트 로그 표**(날짜 · 프로젝트 · 바뀐 영역 · 담당) 첫 줄
3. 마스터: 루트 섹션 `🌏 <이름>`(fill 20,21,23) → (가로지르는 기능이면) `<이름> 진입` 섹션 + `APP` + `WEB`(fill 34,35,38) → 각 섹션에 ⚫ 파일 바 → 링크 카드 1장(상태 뱃지형 + **기준 정보 한 줄**)
4. 플로우: `🌊 플로우` 루트 + 플로우 가이드 + APP/WEB 뼈대
5. 설명 바는 라이브러리 "스크린 설명 컴포넌트"를 불러와 인스턴스로 놓는다(색·제목 자동)

→ 왓챠파티·콘상페처럼 손으로 만든 파일이 서로 조금씩 다른 문제가 사라진다.

### B. Δ 만들기 — 프로젝트 파일에서 "이 프레임들을 Core에 넣겠다" (반자동)

디자인 확정 시점에 프로젝트 파일에서:
1. 최종 프레임들을 선택 → 플러그인이 **Core 색인**과 대조해 후보를 보여 줌: "어느 Core › 어느 섹션 › 어느 묶음 (교체/추가)" + 근거(같은 이름의 화면이 있음 / 진입 프레임이 가리킴 / 케이스 축이 같음). 후보가 둘 이상이거나 없으면 AI가 근거를 붙여 추천, 없으면 "새 Core" 제안
2. 수록 기준을 자동 적용해 **뺄 것을 먼저 제안**: 같은 화면·데이터만 다른 것, 입력 상태 3종, 갈래 반복, 재배치 없는 뷰포트 → "대표 1장" (§4-2 표가 그대로 규칙)
3. 디자이너가 체크박스로 확정 → 프로젝트 파일에 **`🔁 Core 반영사항` 페이지**를 만들고 엔트리(Core 위치 링크 · 변경 유형 · 요약 · 최종 프레임 복제 · 담당)를 자동 배치. 브랜치 B의 템플릿(3007:6)이 이 페이지의 원형
4. 진입 프레임이 바뀌면 "다른 Core 입구" 엔트리를 따로 추가 (마커 번호·코어 파일 링크 포함)

→ Δ가 "쓰면 좋은 메모"에서 "버튼 누르면 생기는 것"이 된다.

### C. 이관하기 — 배포 후 Core 파일에서 체크리스트 5단계 (반자동)

Core 파일을 열고 플러그인에서 프로젝트 파일 링크를 넣으면:
1. **버전 저장** — 플러그인이 Named version을 저장 (`2026-09-xx 스텝메이드 고도화 반영 (담당: angela)`)
2. **교체/추가** — Δ 페이지를 읽어 항목별로 안내. 파일 간 복사는 Figma가 플러그인에 허용하지 않으므로 **붙여넣기만 디자이너가** 하고(Cmd+C/V), 붙여넣은 프레임을 플러그인이 알아채서 **자리 잡기·이름 맞추기·설명 바 3단·32px 그리드·껍데기 유지 교체**를 처리. 교체 대상은 기존 프레임의 ID를 남긴 채 내용만 갈아 끼움(링크 보존)
3. **링크 카드 갱신** — 기준 문서 링크 1개 + 기준 정보(프로젝트명·배포일·담당자) 텍스트. 배턴터치면 이전 링크를 아카이브 메모로
4. **커버 로그** — 한 줄 자동 기입
5. **아카이브 안내** — 프로젝트 커버를 ✅ 반영 완료로 바꾸고, 파일 이동은 안내만(플러그인은 파일을 옮길 수 없음)

→ 5단계 중 손이 가는 건 "붙여넣기"와 "확인" 두 가지뿐.

### D. 점검하기 — 어느 Core 파일이든 규격 검사 (완전 자동)

플러그인 창에서 "점검" 누르면 열린 Core 파일을 훑어 어긋난 곳을 목록으로:
- 링크 카드 없음 / 기준 정보 없음 / 링크가 2개 이상
- 설명 바 3단 누락 (크기 바 없는 화면, 파일 바 없는 섹션)
- 프레임 이름 규칙 위반 (크기 접미사 섞임, "Frame 123")
- 32px 그리드 이탈, 섹션 여백 60 이탈
- 플로우: 진입 프레임에 마커 없음, "○○ 코어 파일 링크" 없음, 빈 자리표시("기타 상세 페이지")
- 이중 수록 (같은 화면이 두 Core에) — 색인 대조
- 커버 로그 없음
각 항목에 "자동 고치기" 버튼 (가능한 것만) — 지금 14개 파일의 편차(웹툰 루트 없음, TV 구형식, 카드 없는 8개)를 이걸로 한 번에 정리한다.

## 4. 규칙 엔진에 들어가는 것 (이미 있는 재료)

| 규칙 | 출처 | 코드화 난이도 |
|---|---|---|
| Core 색인 (14개 파일의 페이지·섹션·묶음·화면·링크 카드·진입 프레임) | `core-index/core-index.json` | 됨 — 플러그인이 읽기만 하면 됨. REST로 재생성(`dump-core-file.py` → `build-index-entries.py`) |
| 파일 규격 (페이지·섹션·설명 바·링크 카드·플로우 뼈대) | 지침서 §6 | 됨 — A·D 기능의 본체 |
| 판별 신호 3개 + 유형 A/B/C | 지침서 §3 | 신호 1·2는 이름·링크 매칭으로 됨. 신호 3(케이스 축)과 최종 선택은 AI |
| 빈 자리표시 진입 프레임 판정 (번호 마커 → 홈 로우) | `trace-entry-markers.py` | 됨 |
| 수록 기준 (디폴트 2장·승격 3조건·대표 크기·§4-2 표) | 지침서 §4 | 절반 — "같은 화면·데이터만 다름"은 이름/구조 비교로, "반쪽 분기"는 AI 또는 디자이너 체크 |
| 이관 체크리스트 5단계 | 운영안 §6 | 됨 (파일 이동만 안내) |

## 5. 단계별 계획 — 자동화 가치가 크고 판단이 필요 없는 것부터

| 단계 | 만드는 것 | 왜 이 순서 | 완료 기준 |
|---|---|---|---|
| **0 (완료)** | 색인 14개 · 지침서 v0.1+§6 · REST 읽기 스크립트 · 마커 추적기 · 시연 1건 | 규칙이 실물과 맞는지 먼저 확인 | 됨 |
| **1** | 플러그인 뼈대 + **A 새 Core 만들기** + **D 점검하기** | 판단이 전혀 필요 없고, 통일성 효과가 즉시 남(14개 파일 정리). 플러그인 기술 검증(섹션 생성·라이브러리 인스턴스·버전 저장) | 스텝메이드용 새 Core를 플러그인으로 생성 → 왓챠파티와 구조가 같음. 14개 파일 점검 결과 목록이 나옴 |
| **2** | **C 이관하기** (붙여넣기 감지 · 배치 · 링크 카드 · 커버 로그 · 버전) | 이관이 가장 귀찮은 일. 규칙만으로 됨 | 로그인/온보딩 파일럿을 플러그인으로 재현했을 때 손으로 한 결과와 같음 |
| **3** | **B Δ 만들기** (색인 대조 후보 → 수록 기준 적용 → Δ 페이지 생성) + AI 판단 연결 | 판단이 들어가는 부분. 1·2단계에서 색인·규칙이 안정된 뒤 | 스텝메이드·소식함 두 케이스에서 사람 판단과 일치 |
| **4** | 팀 배포 (조직 비공개 플러그인) · 사용 안내 1장 · 색인 자동 갱신 · 규칙 바뀔 때 반영 절차 | 다른 디자이너가 쓰기 시작 | 디자이너 2명이 실제 프로젝트 1건씩 이관 완료 |

Ken이 정하면 좋은 것: 1단계에 들어갈 두 기능(A·D) 순서와, 플러그인 창의 말투·이름.

## 6. 역할과 규칙 운영

- **Ken**: 규칙의 주인. 수록 기준·규격이 바뀌면 노션 운영안 → 지침서 → 규칙 엔진 순으로 반영. 플러그인 화면·문구 확정.
- **Claude(이 저장소)**: 플러그인 코드·규칙 엔진·색인 유지, 시연·검증, 워크로그.
- **디자이너들**: 쓰고 걸리는 점을 알려 줌. 규칙 원칙은 그대로 — "실제로 깨지는 문제가 있을 때만 규칙을 만든다".
- 색인은 배포 이관이 끝날 때마다 플러그인이 REST로 그 Core를 다시 읽어 갱신 → 색인이 오래되는 문제 없음.

## 7. 알아 둘 제약 (설계에 이미 반영)

- 플러그인은 **열린 파일에만 쓸 수 있고, 파일 간 프레임 복사는 못 한다** → C에서 붙여넣기는 사람이, 나머지는 플러그인이.
- 파일 생성·이동·삭제는 플러그인이 못 한다 → 빈 파일 만들기·아카이브 이동은 안내로. (Ken 질문 2026-09-10 "플러그인으로 새 파일을 만들고 거기에 Core를 정리할 수 있나?" → **파일 만들기와 다른 파일의 화면 가져오기, 이 둘은 플러그인이 못 한다.** 그 안에서 규격대로 정리하는 것은 전부 된다. 파일 만들기는 ① 디자이너가 템플릿 파일을 복제(1클릭) ② Claude 쪽 Figma MCP `create_new_file`(폴더 지정 가능)로 대신 만들기 중 택일. 화면 가져오기는 붙여넣기(Cmd+C/V)가 유일하게 원본을 그대로 보존하는 길 — REST로 읽어 다시 그리는 방식은 인스턴스·이미지가 깨져 쓰지 않는다.)
- 다른 파일을 읽으려면 디자이너의 Figma 토큰이 필요 → 처음 한 번 등록. 폴더 목록까지 보려면 토큰에 `projects:read`.
- AI 호출은 키 관리 때문에 작은 중계 서버가 필요 → 3단계에서. 그 전까지 AI 없이도 A·C·D는 다 된다.
- 라이브러리 "스크린 설명 컴포넌트"의 컴포넌트 키를 플러그인에 박아야 함 → 1단계 첫 작업.
