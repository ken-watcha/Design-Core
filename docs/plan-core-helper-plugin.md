# Core 도우미 설계안 v2 — "링크 하나 주면 끝까지" (2026-09-10)

> Ken의 요구(원문 흐름): 스텝메이드 고도화 프로젝트 문서를 정리했다 → 그 **링크를 프로그램에 준다** → 프로그램이 **어느 Core의 어느 부분을 업데이트해야 하는지 알려 주고 진행까지 한다** → **어느 Core에도 해당이 안 되면 노션 운영안의 규칙에 따라 새 Core 파일로 등극**시킨다.
> v1(Figma 플러그인)은 디자이너가 파일을 열고 버튼을 눌러야 해서 접었다. v2는 사람이 하는 일을 "링크 주기"와 "결과 확인" 둘로 줄인다.

## 1. 형태 — 클라우드에서 도는 도우미, 디자이너는 설치할 것 없음

```
디자이너: 프로젝트 링크를 요청 창구에 올린다 (Notion "Core 반영 요청" 표 한 줄, 또는 Slack 한 줄)
   │
   ▼
Core 도우미 (Claude Code 클라우드 세션, 예약 실행 또는 요청 즉시)
   ├─ 읽기   Figma REST ─ 프로젝트 문서 · Core 14개 (색인 갱신)
   ├─ 판단   규칙 엔진(색인·수록 기준·규격) + Claude 판단 → Core 판별 · Δ 목록 · 유형 A/B/C
   ├─ 실행   Figma 연결(use_figma) ─ 어느 파일이든 키만 있으면 쓰기 · create_new_file ─ 새 파일 생성
   └─ 보고   프로젝트 파일에 🔁 Core 반영사항 페이지 · 요청 표에 결과 · 워크로그
```

- 디자이너 쪽엔 **아무것도 설치하지 않는다.** 링크를 올리는 곳(요청 창구)만 있다.
- 실행 주체는 이 저장소의 도우미다. 지금 세션에서 확인된 능력만 쓴다: REST 읽기(토큰 주입), `use_figma`로 **열려 있지 않은 파일에도 쓰기**(세션 1·2에서 번역·페이지 생성에 사용), `create_new_file`(폴더 지정 가능), Notion 읽기/쓰기, 예약 실행(Routine).
- Figma 플러그인은 나중에 "점검하기"(규격 검사) 한 가지만 남길지 결정. 핵심 흐름엔 없다.

## 2. 흐름 — 링크 접수부터 등극까지 (무엇이 자동인지)

| 단계 | 도우미가 하는 일 | 자동? |
|---|---|---|
| ① 접수 | 요청 창구에서 새 링크를 읽는다. 커버 배지로 프로젝트 문서인지 확인, 담당·상태(Working/Final) 읽기 | 자동 |
| ② 읽기 | 프로젝트 문서의 최종 페이지를 읽어 화면 목록·케이스 축·진입 경로 정리. Core 14개 색인을 최신으로 | 자동 |
| ③ 판별 | 지침서 §3: 신호 1·2·3 → 유형 A(기존 Core) / B(여러 Core) / C(새 Core). 빈 자리표시 프레임은 번호 마커 추적으로 판정 | 자동 (근거를 제안서에 남김) |
| ④ Δ 작성 | §4 수록 기준으로 "무엇을 몇 장" 결정, 뺄 것 명시, 입구(다른 Core 플로우) 항목, 링크 카드 기준 정보 | 자동 |
| ⑤ 확인 | 제안서를 요청 표에 붙이고 담당 디자이너에게 "실행할까요?" 한 번 묻는다. **Ken이 원하면 이 단계를 끄고 완전 자동**(버전 저장이 되돌리기 역할) | 스위치 |
| ⑥-A 기존 Core 갱신 | 버전 저장 → Δ대로 교체/추가(껍데기 유지) → 설명 바 3단·32px 그리드 → 링크 카드 갱신 → 커버 로그 → 다른 Core 플로우에 입구·마커·코어 파일 링크 | 자동 (§4 참고) |
| ⑥-C 새 Core 등극 | 운영안 §5 규칙으로 "새 Core" 판정 시: 새 파일 생성(폴더 지정) → §6 규격 뼈대(페이지 4개·Cover·마스터 루트/진입/APP/WEB·설명 바·링크 카드·플로우) → 화면 채우기 → 다른 Core에 입구 | 자동 (화면 채우기는 §4의 방법으로) |
| ⑦ 마무리 | 프로젝트 파일에 🔁 Core 반영사항 페이지 기록, 커버 ✅ 반영 완료, 색인 갱신, 요청 표에 결과 링크(node-id) | 자동. 파일을 아카이브 폴더로 옮기는 것만 사람 (API 없음) |

배포 전(커버 Working)에 접수되면 ①~④까지만 하고 제안서를 남긴다. 배지가 Final로 바뀌면(또는 요청 표에 "배포됨" 체크) ⑤부터 이어 간다 — 운영안 "배포 전 시안은 마스터에 못 들어온다".

## 3. 할 수 있는 것과 없는 것 — 세션에서 확인된 사실 기준

| 일 | 가능 | 근거 |
|---|---|---|
| 어떤 파일이든 읽기 | 됨 | REST `files/:key/nodes` — 이 세션에서 Core 14개 + 프로젝트 문서 통째로 읽음 |
| 열려 있지 않은 파일에 쓰기 (페이지·섹션·프레임·텍스트·인스턴스 생성, 이름·위치 변경, 버전 저장) | 됨 | `use_figma`는 파일 키만으로 실행. 세션 1·2에서 번역 202노드·마스터 페이지 생성에 사용 |
| 새 파일 만들기 (폴더 지정) | 됨 | Figma 연결의 `create_new_file` (팀 키 `organization::1014901253946075002`, 프로젝트 ID 지정) |
| 설명 바·링크 카드를 라이브러리 컴포넌트로 놓기 | 됨 | `importComponentByKeyAsync` + 속성 설정 (세션 2 파일럿에서 확인) |
| **다른 파일의 화면을 그대로 옮기기** | **안 됨(직접은)** | Figma API에 파일 간 복사가 없음. §4에서 우회 |
| 파일 이동·이름 변경·삭제 | 안 됨 | API 없음 → 안내 (Ken이 1클릭) |
| Notion 요청 표 읽기·결과 쓰기 | 됨 | Notion 연결 (운영안·개편안 읽기에 사용) |
| 예약·즉시 실행 | 됨 | Routine(create_trigger): 매시간 요청 표를 보거나, 요청 즉시 |

## 4. 핵심 난제 하나 — 화면을 프로젝트 파일에서 Core 파일로 옮기기

Figma는 API로 파일 간 복사를 막아 놓았다. `clone()`은 **같은 파일 안에서는 페이지를 넘어도 되지만** 다른 파일로는 안 된다. "전부 자동"이 되려면 이 하나를 넘어야 하는데, **넘지 않는다** — 넘으려는 순간 토큰이 든다(2026-09-18 Ken 결정, 지침서 §0-8).

| 방법 | 어떻게 | 원본 보존 | 언제 |
|---|---|---|---|
| **2′. 복제해서 깎기** (채택) | 사람이 프로젝트 파일을 **Duplicate**(1클릭) → `[Core] <이름>`으로 이름·폴더 → 도우미가 **복제본 안에서** `🌏 마스터 파일`을 같은 파일 `clone()`으로 채우고 → 작업 페이지(✅ Mobile·✅ Web·📏 운영 가이드)를 **삭제**. 새 파일이 곧 Core, 원본 프로젝트 문서는 기준 문서로 무수정 | 완전 | 새 Core (⑥-C). 토큰: 화면 1장에 `clone()` 한 줄 |
| **3. 붙여넣기 요청** | 다른 Core의 화면이 필요할 때(진입 섹션의 홈 사본) "이 프레임을 여기 붙여 넣어 주세요" 링크로 요청. 붙여 넣으면 도우미가 자리·마커를 정리. 안 붙여 넣으면 **하이퍼링크**로 둔다 | 완전 | 파일 경계 예외 |
| ~~1. 깊은 복제~~ (폐기) | 화면 속성을 읽어 다른 파일에 다시 그린다. 스파이크(`docs/spike-2026-09-10-deep-clone.md`)로 "된다"까지는 확인했고 도구(`scripts/figma-write/build-clone-spec.py`·`clone-lib.js`·`compose-clone-job.py`)도 남겼지만, **홈 1장에 코드 ~150KB를 다시 써 넣어야 해서 토큰을 그대로 태운다**(2026-09-18 스텝메이드 진입 섹션에서 Ken 중단). 라이브러리 버전 차이로 오버라이드도 어긋난다 | — | 쓰지 않는다 |
| ~~2. 프로젝트 파일이 Core가 됨(v0.2 해석)~~ | 프로젝트 파일 **안에** 마스터 페이지를 얹는다 — 도우미가 Ken 뜻을 잘못 읽은 것. Ken 뜻은 "새 파일을 만들어 Core로"(2026-09-18) → 2′로 대체 | — | — |

기존 Core 갱신(⑥-A/B)에서 프로젝트 화면을 Core 파일로 넣는 것도 같은 파일 경계다 → 3(붙여넣기 요청) 또는 3단계 검증 때 다시 정한다.

## 5. 안전장치 — "자동"이 무서운 것이 되지 않게

- 모든 쓰기 전에 **Named version 저장** ("2026-09-xx 스텝메이드 고도화 반영 전"). 되돌리기는 버전 복원 1클릭.
- 처음 몇 건은 **Core 파일의 브랜치**에서 실행 → 담당자가 머지. 안정되면 본 파일에 직접.
- 실행 로그: 무엇을 몇 개 만들고 바꿨는지 node-id 링크로 요청 표에 남김.
- ⑤ 확인 스위치는 팀이 익숙해질 때까지 켜 둔다. 운영안의 "담당 디자이너가 확인" 원칙과 맞는다.
- 도우미가 확신도 "낮음"이면 실행하지 않고 제안서만 남긴다.

## 6-1. 실행 주체 (Ken 결정 2026-09-10)

처음엔 **Ken의 계정·토큰 하나**로 실행한다(요청은 누구나 올림). 완성 후 팀에 전달할 때는 **디자이너마다 자기 환경(같은 저장소 + 자기 Figma 토큰)을 연결**해서, 표에 올린 사람의 세션이 실행한다. 규칙은 저장소 하나에 있으므로 누가 돌려도 결과가 같다.

## 7. Ken이 정할 것

1. 요청 창구: **Notion 표** vs **Slack 채널** (Notion이 상태·이력이 남아 권장)
2. ⑤ 확인 단계를 켜 둘지(권장: 처음엔 켬), 끄면 어떤 조건에서
3. 스파이크 진행 허가: 테스트용 새 파일을 Core 폴더가 아닌 곳(예: Drafts 또는 지정 폴더)에 만들어 스텝메이드 화면 1장을 복제해 봐도 되는지
4. 새 Core 파일 이름 규칙 확인: `[Core] <프로젝트 커버의 Page Name>` (왓챠파티·소식함 선례)
