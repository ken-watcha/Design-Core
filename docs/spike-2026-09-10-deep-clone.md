## 확인된 한계 2개

1. **이미지 해시는 파일 경계를 넘지 못한다.** 왓챠파티 Core의 이미지 해시 3개를 브랜치에서 `getImageByHash`로 찾으면 전부 null. 이미지를 옮기려면 바이트를 옮겨야 하는데, `use_figma` 실행 환경엔 `fetch`가 없고 코드 길이 한도(50,000자)가 있어 **약 30KB 이하 이미지만** base64로 통과한다. 포스터급(200~700KB)은 불가.
   → **추가 시험 (같은 날 저녁)**: Figma 연결에는 이 용도의 전용 통로가 있다 — `download_assets`(원본 이미지 바이트를 내려받는 주소) → `upload_assets`(대상 파일의 지정 노드에 이미지 채우기로 올리는 주소). 왓챠파티 화면 `5:14326`의 원본 이미지 20장 주소를 받아 2장(95KB·256KB)을 **내려받는 데는 성공**했다. 그러나 올리는 주소가 `mcp.figma.com`이라 Design-Core 환경의 허용 목록(`api.figma.com`·`www.figma.com`)에 없어 **프록시에서 거부**(`connect_rejected` 403, 프록시 상태 페이지에서 확인). Ken이 `mcp.figma.com`을 허용 목록에 추가하면 새 세션부터 큰 이미지도 자동으로 옮겨진다. 시험용 빈 사각형 2개는 브랜치의 `3413:299`에 남겨 두었다(다음 세션에 재시험).
   → **해결 (2026-09-10 세션 5, Ken이 `mcp.figma.com` 허용 후)**: 같은 두 장(95KB·256KB)을 `upload_assets` 주소로 POST → 200 성공, 이미지 해시 반환. 단 **"지정 노드에 자동으로 채우기"(nodeIds)는 이 시험에서는 일어나지 않았다**(다음 날 같은 절차로 홈 롱 이미지 2장을 올릴 땐 자동 배치됨 — 표본 2개라 안전장치로 해시 지정을 항상 둔다) — 사각형은 단색 그대로였고 파일 어디에도 새 이미지 노드가 없었다(본 파일도 확인, 깨끗함). 대신 올리기 응답의 `imageHash`가 이미 그 파일의 이미지 저장소에 들어가 있어(`getImageByHash(해시).getSizeAsync()` = 280×157·500×500), `use_figma`로 그 해시를 채우기에 넣으니 바로 렌더됐다. 결과: `docs/img/spike-image-transfer-result-2026-09-10.png` (원본 2장이 브랜치 사각형에 들어감). **최종 절차 = download_assets → curl 내려받기 → upload_assets(count) → curl -F POST → 응답의 해시를 `use_figma`로 대상 노드 fills에 지정** (`scripts/figma-write/deep-clone.md` 3단계).
2. **인스턴스 교체 속성이 로컬 컴포넌트를 가리키면** (하단바 활성 탭의 `Instance#…: "9:1043"`) 대상 파일엔 그 ID가 없어 기본값으로 남는다.

## 그래서 "화면 옮기기"의 최종 방법

| 화면 종류 | 방법 | 자동화 |
|---|---|---|
| 라이브러리 인스턴스 + 텍스트로 된 화면 (왓챠 화면 대부분) | 깊은 복제 | 자동 |
| 작은 이미지(아이콘·로고, ≤30KB)가 있는 화면 | 깊은 복제 + 이미지 base64 전송 | 자동 |
| 큰 이미지(포스터·배너)가 있는 화면 | 깊은 복제 + **`download_assets` → `upload_assets`로 바이트 이관 → 응답의 해시를 `use_figma`로 채우기에 지정** (`mcp.figma.com` 허용됨, 2026-09-10 세션 5 검증) | **자동** |
| 새 Core (프로젝트 파일이 Core가 되는 경우) | 같은 파일 안 복제 → 옮길 것 없음 | 자동 |

Core 마스터의 포스터는 더미 데이터라, 자리표시로 두고 담당자가 원하면 채우는 정책도 가능 (Ken 결정).
