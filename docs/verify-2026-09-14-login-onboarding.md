### 3-1. 규칙과 실물이 다른 점 1건 — 입력 화면의 대표 상태

지침서 v0.2 §4-2 는 "focus / active / filled → 대표 1장 (filled)"인데, Ken 손 결과는 이름·비밀번호는 **active**(입력 중, 키보드 노출), 재입력만 filled 를 골랐다. 장수는 같으니 판단 재현은 통과했지만, "복붙"할 원본이 달라지므로 실행 재현 전에 정해야 한다.
- 안 1: 규칙을 "대표 1장 = **active**(입력 중 상태가 가장 많은 정보를 보여 줌: 키보드·도움말·버튼 상태)"로 고친다 → 손 결과와 일치
- 안 2: 규칙은 filled 로 두고 손 결과를 예외로 본다 → 재현 결과가 손 결과와 2장(APP)+2장(WEB) 다름
- **도우미 권장: 안 1.** 근거: 재입력 화면은 active 가 없고(재입력- active 는 자손 261 로 다른 구성) filled 가 곧 마지막 상태라 예외가 아니라 "마지막으로 채워진 상태 = 가장 많은 결정을 보여 주는 상태"로 읽힌다.

### 3-2. 도우미가 새로 배운 규칙 (v0.3 후보)

1. **프레임 이름은 문서를 믿지 않는다.** 기준 문서의 원본 22장 중 7장이 번호("1", "2", "3", "22")나 오기("표시 콘텐츠 설정")였다. 이름은 화면 안 제목 글자(가장 큰 텍스트)로 짓고, 손 결과의 이름 규칙을 따른다: "이메일 입력", "가입 시작 안내", "가입 완료", "로그인/가입 방법 선택".
2. **같은 지문의 중복 프레임은 1장.** `비밀번호 - filled` 와 `비밀번호 재입력 - filled` 는 글자·자손 수가 같았다(문서의 복사 잔재). 이름이 아니라 지문으로 중복을 잡는다.
3. **짝표를 먼저 만들고 복붙한다.** 지문(보이는 글자 8개 + 자손 수)이 원본에 정확히 1개면 확정, 2개 이상이면 이름으로, 0개면 사람에게 묻는다. 이 짝표가 곧 "복붙 + 원본 대조"의 대조 기준이다.
4. **문서 머리말을 읽는다.** "로그인 과정은 변경이 없으며 회원가입 과정만 변경" 한 줄이 3-1·3-2(로그인 화면)를 "유지"로 분류하는 근거였다.

### 3-3. Ken 확인 사항

- §3-1 입력 대표 상태: 안 1(active)로 규칙을 고쳐도 되나?
- 마스터에 **기존 회원 로그인(비밀번호 입력, 3-1·3-2)** 화면이 없다. 파일럿 범위가 "회원가입만"이었기 때문인지, 아니면 넣어야 하는데 빠진 것인지. (Core 로그인/온보딩 전체로 보면 로그인 화면도 결정 지점이다)

## 4. 실행 재현 — 하려면 필요한 것

1. Ken이 `[Core] 로그인/온보딩` 파일에 브랜치 **"Core 도우미"**를 만들고 브랜치 URL(`.../branch/<브랜치키>/...`)을 준다. API로는 브랜치를 만들 수 없다.
2. 도우미가 브랜치에 페이지 `🌏 마스터 파일 (도우미 재현)`을 만들고, §2 짝표의 원본 22장을 **같은 파일 안 복제**(`clone()` → 섹션에 `appendChild`)로 손 결과와 같은 좌표에 놓는다. 바 24개(⚪️ 2 + 🔵 22)는 손 결과의 인스턴스를 복제해 제목만 맞춘다. 링크 카드도 복제.
3. 대조: 재현 페이지의 프레임 22장과 손 결과 22장을 이름·크기·좌표·자손 수로 비교 → 차이 0이면 통과. 복제 후 HUG 재계산으로 폭이 바뀌면 원본 값으로 되돌린다(세션 5 기술 사실).
