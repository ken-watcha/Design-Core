# Core 도우미 — Figma 플러그인 (뼈대, 2026-09-18)

프로젝트 파일을 **분석 → 판별 → (새 Core면) 복제본을 Core로 정리 / (기존 Core면) Δ 화면을 골라 붙여 넣게** 도와주는 플러그인. Claude를 실행 중에 부르지 않는다. 판단은 전부 `rules.json`(규칙)과 `core-index/core-index.json`(Core 색인)으로 하고, 두 파일은 플러그인이 켜질 때 GitHub main에서 받아 온다 → **재설치 없이 규칙만 고치면 다음 실행부터 반영.**

## 파일

| 파일 | 역할 |
|---|---|
| `manifest.json` | 플러그인 정의. 네트워크는 `raw.githubusercontent.com`만 허용 |
| `rules.json` | 규칙 원본(바닥값). 크기 클래스·마스터 페이지 규격·배치 숫자·설명 바 컴포넌트 키·삭제할 페이지·판별 임계값·불용어·검토 주기와 검토자 |
| `memory.json` | 기억 공유본(승인된 기억 + 대기 가설). 플러그인 "기억 내보내기" 결과를 넣는다 |
| `code.js` | Figma 안에서 도는 쪽. 분석·판별·복제본 정리·붙여 넣은 화면 배치 |
| `ui.html` | 화면. 분석·판별 → 계획 → 실행 + 학습 검토 + 채점표·내보내기·가져오기 |

## 설치 (개발 플러그인, 각자 노트북)

1. 이 저장소를 받는다(`git clone` 또는 ZIP 다운로드). `plugin/` 폴더가 있으면 된다.
2. Figma 데스크톱 앱 → 아무 디자인 파일 열기 → 메뉴 **Plugins → Development → Import plugin from manifest…** → `plugin/manifest.json` 선택.
3. 이후 **Plugins → Development → Core 도우미**로 실행. 규칙·색인은 실행마다 GitHub에서 내려받으니 저장소를 다시 받을 필요는 없다(플러그인 코드 자체가 바뀔 때만 다시 받는다 → Organization 비공개 게시로 넘어가면 그마저도 자동).

## 사용 흐름

### 새 Core (프로젝트 문서가 기존 Core에 안 들어맞을 때)

1. **프로젝트 파일**에서 플러그인 실행 → **분석** → 파일 종류(프로젝트/Core)·커버 정보·APP/WEB 크기별 후보 화면·수록 대조표·판별 후보가 나온다.
2. 크기별 후보가 틀리면 드롭다운으로 고친다. 판별 후보에서 **새 Core**를 고르고 **계획 저장**.
3. 안내대로 사람이 **File → Duplicate**(복제는 API로 못 한다) → 복제본 이름을 `[Core] ○○`로.
4. **복제본**에서 플러그인 실행 → 저장된 계획이 보이면 **복제본에 Core 만들기** → `🌏 마스터 파일` 페이지(링크 카드 + APP 3장 + WEB 4장, 설명 바 포함)를 만들고, 원본 화면과 대조(차이 0)한 뒤 작업 페이지(✅ Mobile / ✅ Web / 📏 운영 가이드 / ㄴ 로컬 컴포넌트)를 지운다. 로컬 컴포넌트 인스턴스는 먼저 분리(detach).
5. 남는 것: Cover / --- / 🌏 마스터 파일. Named version·파일 이동·색인 갱신은 사람이.

### 기존 Core 갱신

1. 프로젝트 파일에서 **분석** → 판별 후보에서 해당 Core를 고르고 **계획 저장**.
2. **Δ 화면 선택** → 바꿀 화면들이 선택된다 → ⌘C.
3. 그 Core 파일의 브랜치 **"Core 도우미"**를 열고 ⌘V → 플러그인 실행 → **붙여 넣은 화면 배치** → 마스터 규격 자리에 놓인다. (v1은 배치까지. 기존 화면과의 대조는 다음 단계)

## 배우는 방식 — 가설을 쌓고, 검토자가 승인한 것만 배운다

"진행"을 눌렀다고 정답은 아니다(마구 누를 수 있다). 그래서 플러그인은 **바로 배우지 않는다.**

1. **가설** — 진행을 누를 때마다 그 실행에서 배울 수 있는 것을 항목으로 뽑아 대기함에 넣는다. ① 섹션 이름 → 크기 ② 어떤 이름의 화면을 대표로 골랐나(제친 후보 포함) ③ 프로젝트 이름 낱말 → 어느 Core ④ 페이지 구성 → 파일 종류. 항목마다 근거를 붙인다: 제안 그대로였나 / 사람이 바꿨나 / 확인 필요였나 / 규칙과 같은가.
2. **살펴봤나 표시** — 확인 필요 항목을 하나도 안 건드리고 15초 안에(또는 5초 안에) 눌렀으면 "⚠ 빠른 진행"으로 표시한다. 채점에서도 뺀다. 검토자가 이 묶음은 믿지 않으면 된다.
3. **결과 확인** — 새 Core를 만든 뒤 하루가 지나거나 다른 사람이 그 파일을 열면, 만든 마스터의 화면들이 그대로인지 자동으로 본다. 그대로면 "✓ 유지됨", 누가 바꿨으면 "✗ 바뀜"을 그 가설 묶음에 붙인다.
4. **검토** — 결정 안 된 실행이 **프로젝트 3개**(`rules.json` `review.everyRuns`) 쌓이면 플러그인 위에 "학습 검토할 때입니다"가 뜬다. 검토자(`review.reviewers`, 지금은 Ken. Figma 표시 이름과 같아야 한다)가 목록을 열어 항목마다 **승인 / 거절 / 보류**. "이 묶음 나머지 모두 승인"도 있다.
5. **승인된 것만 기억**이 되어 다음 판단에서 규칙보다 먼저 쓰인다. 거절한 항목은 같은 가설이 다시 오면 "이전에 거절됨 n회"로 표시된다. 되돌림을 누르면 기억에서 빠진다.

묻는 기준은 그대로: 1등과 2등 점수 차가 1 미만일 때만 "확인 필요". 승인된 기억이 쌓일수록 자동이 늘고 묻는 횟수가 준다.

**여러 노트북** — 가설은 그 노트북과 그 Figma 파일(복제·브랜치에 따라감)에 남는다. 다른 디자이너의 가설을 검토하려면: 그 사람이 "기억 내보내기" → JSON을 검토자에게 → 검토자가 "붙여 넣은 기억 가져오기" → 검토 → 검토자가 "기억 내보내기"한 것을 `plugin/memory.json`에 커밋 → 모든 노트북이 켤 때 합친다. 이 오가는 부분을 자동으로 하려면 저장 서버(ADP 등)가 필요 — 결정 대기.

`rules.json`은 여전히 바닥값이다. 학습이 없을 때의 기본 판단과 배치 숫자·컴포넌트 키처럼 배울 수 없는 것만 담는다.

## 학습이 제대로 가는지 보는 법 (채점표)

플러그인 위쪽 한 줄과 "학습 채점표" 접기 칸에 늘 보인다. 빠른 진행은 세지 않는다.

| 숫자 | 뜻 | 좋은 방향 |
|---|---|---|
| 적중 n/m | 최근 살펴본 실행에서 제안을 그대로 채택한 비율 | 올라간다 (앞 절반 → 뒤 절반) |
| 확인 요청 | "확인 필요"로 표시된 항목 수 | 내려간다 |
| 사람이 고친 | 제안을 바꾼 횟수 | 내려간다 |
| **승인된 기억의 오답** | 승인된 기억을 근거로 제안한 것을 사람이 고친 횟수 | **0이어야 한다.** 생기면 그 승인이 틀린 것 → 검토 목록에서 되돌림 |
| 판별 적중 | 새 Core/기존 Core 판별이 맞은 횟수 | 올라간다 |
| 가설/승인/거절 | 대기함 항목 수와 결정 | 거절 비율이 줄면 제안이 좋아지는 것 |
| 마스터 유지/바뀜 | 만든 뒤 그대로였나 | 바뀜이 0 |
| 기억이 갈리는 항목 | 같은 섹션 이름이 두 크기로, 같은 낱말이 두 Core로 승인된 것 | 없어야 한다 |

판정 한 줄: `데이터 부족` → `보통` → `나아지는 중` → `잘 가는 중` / 경고 `마스터가 나중에 바뀜`, `빠른 진행이 대부분`, `승인된 기억의 오답`, `기억이 갈림`, `적중률 하락`.

결과물 자체(마스터 화면이 원본과 같은가)는 학습과 무관하게 매번 복제 뒤 대조로 확인한다.

## 게시 (나중, Organization 플랜)

Figma → Plugins → Development → Core 도우미 → **Publish** → 공개 범위 "Organization only". 이후 각자 노트북에서 Plugins에서 설치, 새 버전은 자동 반영. 게시 전에는 위 개발 플러그인 방식으로 시험한다.
